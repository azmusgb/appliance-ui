## Global constraints (`AGENTS.md`, `DESIGN.md`)

- This repo is the source. Never edit a consumer's copy or `dist/` by hand; `npm run build` writes `dist/`, committed.
- `npm ci && npm test` before every PR, counts pasted. A release bumps `version` in `tokens.json` and `package.json`
  together with one `CHANGELOG.md` entry naming its audience.
- After a colour change: `npm run contrast`, commit `docs/contrast.md`. No hand-written literal; `npm run literals`
  must not grow.
- A sync is its own PR in the consumer, opened from here; it never merges. The owner merges each PR by number.
- A read that failed or is unknown is its own state, in the sentence too, with a failed-source test per new read.
- S2's rules hold for every new sentence: at most two, each at most 60 characters, the same input always the same words,
  an estimate only when the source gave one, stale in the past tense with its age and source.
- Another session works in this repo. Before a release: `ListAgents`, `gh pr list`, re-read `main` before taking a
  version number.

## Decisions this plan makes (for the owner's review)

None changes a spec. If the owner disagrees with one, it changes here.

1. **Which pages speak.** A page gets a sentence only if it has a reading. Proposed: lab, quick, movies, papers, lists,
   drives, lights, internet, weather, health, backups, versions, alerts, automations, missions. Not: wall (spec
   non-goal), scan, print, settings and its tabs, map, privacy, mission detail (they are forms, lists of links or one
   record; their head stays the page name). Rejected: every page speaks, which forces sentences that report nothing.
2. **One kit release per rail area, not per page.** The spec says a page's sentence is "written … in the PR that moves
   them", and also that no app writes sentence text, so the words must ship in the kit first. Four releases (Workshop,
   Household, Network, System) keep each review to about four pages of wording; Pi Hub then moves one page per PR. Costs
   up to four more syncs. Rejected: one release for all fifteen (too much wording to review at once); one per page
   (fifteen syncs).
3. **Who didn't answer.** An `unavailable` reading may name what failed (`reading.unanswered`, a short name). With it
   the head says "{unanswered} isn't answering." and "The {name} wasn't read."; without it, today's words. This is
   rule 5's phrase with the right subject, not a new state. Rejected: Pi Hub writing its own line (breaks "no app writes
   sentence text").
4. **The job line stays as S3 draws it.** No change unless the owner says the 1440 px look is wrong; then it is a
   one-line spec edit plus a patch release, not a silent kit change.
5. **axe-core becomes a dev dependency** (audit row 13): the repo rule asks for axe where a repo has it, and the kit's
   own sweep cannot see contrast or ARIA misuse. Dev-only; nothing ships to a consumer. Rejected: keep the hand sweep.
6. **A touch-target token** (row 14): `tokens.json` gains `target` (44 px) and the 23 hand-written `44px` use it. A new
   token is a contract change, so `DESIGN.md` changes in the same PR. Rejected: leave them, which keeps the literals
   check blind to sizes.
7. **The breadcrumb is Pi Hub's to fix** (row 4), in Pi Hub's own CSS; the kit gains no breadcrumb part until a second
   app draws one.
8. **Not in this plan:** `lab-designs` and `lab-tools` (baseline step 15 builds them); a kit row for Local AI's
   Research page (needs the owner's word that it is a page of the platform).
